# Code style

These rules apply to every file you create or edit in this project. There are
no exceptions: a rule is never skipped because a case is small, temporary,
generated by you in a hurry, or "obviously fine". If a rule seems impossible to
follow in some case, restructure the code until it can be followed.

Where this skill conflicts with `nextjs-architecture`, `responsive-tailwind`
or `styling-tailwind-scss`, this skill wins. When you edit a file that breaks
these rules, bring the whole file in line as part of the same change.

## 1. Naming

A reader must understand what a thing does from its name alone, without
opening it.

- Functions, methods, components, hooks and SCSS mixins are never named with
  one or two characters. `go`, `cn`, `mq`, `fn`, `cb` are all forbidden.
- Use full words, not abbreviations: `getModelImageAvailability`, not
  `getImgAvail`; `handleSubmit`, not `onSub`.
- Functions and methods start with a verb that says what they do:
  `formatPrice`, `selectPreorderModel`, `createRateLimiter`.
- Event handlers are `handle<Event>` inside a component and `on<Event>` as a
  prop: `handleQuantityChange`, `onQuantityChange`.
- Booleans read as a statement: `isOpen`, `hasError`, `canSubmit`.
- Components are nouns describing what is rendered: `TestimonialCard`,
  `SlideControls`.
- Variables, parameters and type names follow the same standard: full words,
  no single letters, no abbreviations. `event` not `e`, `index` not `i`,
  `deltaX` not `dx`, `database` not `db`, `previousValue` not `prev`.

Wrong:

```ts
const go = (dir: number) => setIdx((i) => i + dir);
```

Right:

```ts
const showSlideByOffset = (offset: number): void => {
  setActiveSlideIndex((currentIndex: number): number => currentIndex + offset);
};
```

## 2. Folders and files

Everything that belongs to one thing lives in that thing's own folder. A
file that serves a single component or a single module never lies next to
unrelated files.

### Component folders

- Every component has its own folder. The folder is named exactly like the
  component, in PascalCase, always starting with a capital letter:
  `ui/Input/`, `ui/DronePlaceholder/`, `sections/Hero/`.
- The component file is always `index.tsx`. It is the only `.tsx` file in the
  folder. Two components never share a folder: `Button` and `ButtonLink` are
  `ui/Button/index.tsx` and `ui/ButtonLink/index.tsx`.
- Everything that belongs only to that component sits next to its
  `index.tsx`:
  - `types.ts` — the props type and every other type of the component
  - `styles.module.scss` — its SCSS module
  - kebab-case helper files — class name builders, id builders, constants
    (`Button/button-class-names.ts`, `Tabs/tab-ids.ts`, `Field/field-ids.ts`)
- A component used by a single parent lives in a subfolder of that parent:
  `sections/Hero/HeroSlider/index.tsx`, `layout/Header/MobileMenu/index.tsx`.
  All sub-components of a section sit one level below the section folder, no
  matter which of them renders which.
- A component is imported by its folder path, without `index`:
  `import { Input } from "@/components/ui/form/Input"`. Its helpers and types
  are imported by file: `"@/components/ui/Button/button-class-names"`,
  `"@/components/ui/Tabs/types"`.
- `index.tsx` holds the component itself. It is never a barrel that
  re-exports other files, and `index.ts` files are not used.
- Next.js route files in `src/app` (`page.tsx`, `layout.tsx`, `route.ts`)
  keep the names Next.js requires.

```
ui/
  Button/
    index.tsx
    button-class-names.ts
    types.ts
  ButtonLink/
    index.tsx
    types.ts
  DronePlaceholder/
    index.tsx
    styles.module.scss
    types.ts
  form/
    form-control-class-names.ts
    Input/
      index.tsx
      types.ts
    Select/
      index.tsx
      styles.module.scss
      types.ts
sections/
  Hero/
    index.tsx
    HeroSlider/
      index.tsx
      styles.module.scss
      types.ts
    HeroStage/
      index.tsx
      styles.module.scss
      types.ts
```

Wrong:

```
ui/
  Button.tsx
  ButtonLink.tsx
  button-class-names.ts
  DronePlaceholder.tsx
  DronePlaceholder.module.scss
  types.ts
```

### Every other folder

- Folders that are not component folders (grouping folders and code folders)
  are full, descriptive words in kebab-case: `components/ui`, `ui/form`,
  `lib/server`, `lib/preorder-selection`. Only component folders start with a
  capital letter.
- Never create folders named `utils2`, `misc`, `common`, `helpers`, `tmp`,
  `stuff`, or abbreviations such as `cmp`, `hk`, `svc`.
- Folder names fixed by Next.js or by the project spec in `CLAUDE.md` stay as
  they are (`app`, `api`, `components/ui`, `lib`, `data`).
- Non-component files are kebab-case and named after their content
  (`rate-limit.ts`, `preorder-selection.ts`).
- In `src/lib` every module has its own folder with the module file and its
  `types.ts`: `lib/server/rate-limit/rate-limit.ts` +
  `lib/server/rate-limit/types.ts`. `lib/` and `lib/server/` contain folders
  only, never loose files.
- A folder never mixes loose files of one thing with folders of other things.
  A loose file is allowed in a grouping folder only when every folder beside
  it uses it and the folder name describes it:
  `ui/form/form-control-class-names.ts` is shared by `Input`, `Select` and
  `Textarea`. A file used by one of them goes into that one's folder.
- Flat collections stay flat while each unit is a single file: `src/data`
  (one file per data set), `src/types` (one file per domain),
  `lib/validation` (one schema per file), `src/styles` (SCSS partials). They
  hold no `types.ts` and no helpers.
- When you add, move or rename a file, ask "what does this file belong to?"
  and put it in that folder. If the answer is "one component", it goes into
  that component's folder.

## 3. No comments

Never write comments. The only file that may contain comments is
`.env.example`.

This covers every comment form in every other file:

- `//` and `/* */` in TypeScript, TSX, SCSS and CSS
- JSDoc blocks
- `{/* */}` in JSX
- `// TODO`, `// FIXME`, commented-out code
- `eslint-disable`, `@ts-ignore`, `@ts-expect-error` and similar directive
  comments — fix the code so the directive is not needed

Directives that are not comments (`"use client"`, `"use server"`,
`import "server-only"`) are fine.

If code needs a comment to be understood, the code is the problem. Rename
things, extract a well-named function or constant, or simplify the logic until
it reads on its own. Explanations for humans go into `README.md`; explanations
for agents go into `CLAUDE.md`.

## 4. Language of agent files

Everything written for agents is in English: every `SKILL.md` (including its
`name` and `description`), `CLAUDE.md`, `AGENTS.md`, agent definitions,
slash commands and any other file under `.claude/`. Code, identifiers, UI copy
and commit messages are in English as well.

## 5. Simple syntax

Write the most obvious version of the code. Someone who knows basic
TypeScript, React and CSS must be able to read every line without stopping.
Longer and plain beats shorter and clever.

In TypeScript and TSX:

- No nested ternaries. One ternary on a simple value is fine; anything more
  becomes `if` / `else` or an early return.
- No control flow through `&&`, `||` or `??` chains. Use `if`. In JSX a single
  `condition && <Element />` is fine; more than one condition is computed into
  a named boolean first.
- No tricks: `!!value`, `~~value`, `+value`, the comma operator, `void 0`,
  bitwise operators, immediately invoked functions, labeled statements.
- Give intermediate results a name instead of chaining long expressions on one
  line.
- Prefer `map`, `filter`, `find` and plain `for...of` loops. Do not use
  `reduce` when a loop says the same thing more clearly.
- Destructure one level deep. No nested destructuring, and no renaming plus
  defaults plus rest combined in a single pattern.
- Keep types simple: plain object types and unions. Avoid conditional types,
  `infer`, recursive types and layered mapped types when a straightforward
  type does the job.
- One statement per line. Functions do one thing and stay short; when a
  function grows several steps, extract each step into a named function.

Wrong:

```tsx
const label = `${value}${suffix ?? ""}${unit ? ` ${unit}` : ""}`;
```

Right:

```tsx
const formatFeatureLabel = (feature: Feature): string => {
  const valueWithSuffix: string = `${feature.value}${feature.suffix ?? ""}`;

  if (feature.unit === undefined) {
    return valueWithSuffix;
  }

  return `${valueWithSuffix} ${feature.unit}`;
};
```

In styles (Tailwind, SCSS, CSS):

- Use plain Tailwind utilities and theme tokens. No arbitrary variants such as
  `[&>li]:mt-2` or `[&:has(input:checked)]:bg-accent`, and no stacks of
  arbitrary values; move such styling into a SCSS module with a clearly named
  class.
- In SCSS, write plain rules with one clearly named class per element. Nest at
  most two levels deep.
- No `@extend`, `@each`, `@for`, `@if`, SCSS functions, maps or placeholder
  selectors when plain, written-out rules work.
- Keep selectors short. No long descendant chains and no specificity battles.
- No `!important`.
- No dense one-line shorthands that hide several values when separate
  properties are clearer.

## 6. Arrow functions by default

Write functions as arrow functions assigned to a `const`. This is the default
for components, hooks, event handlers, utilities, route handlers and
callbacks. Use a function declaration only when an arrow function cannot do
the job or would be harder to read:

- the function needs its own `this`, or is a generator (`function*`)
- the function has overload signatures
- the function is generic and lives in a `.tsx` file, where the arrow form
  needs the `<Type,>` workaround
- the function must be hoisted because it is called above its definition and
  the code cannot be reordered

Nothing else counts as a need. "It is a component", "it is exported" or "it is
long" are not reasons for a function declaration.

- Always use a block body with an explicit `return` for anything longer than
  one short expression.
- Next.js files that require a default export define the arrow function first
  and export it at the end of the file (see section 10).

Wrong:

```tsx
function formatPrice(priceUsd: number): string {
  return usdFormatter.format(priceUsd);
}

export default function HomePage(): JSX.Element {
  return <main />;
}
```

Right:

```tsx
const formatPrice = (priceUsd: number): string => {
  return usdFormatter.format(priceUsd);
};

const HomePage = (): JSX.Element => {
  return <main />;
};

export default HomePage;
```

## 7. Component props

A component takes a single parameter named `props` and reads its values into
constants on the first line of the body. Never destructure props inside the
parameter parentheses. Default values are set in that body destructuring.

Wrong:

```tsx
const FeatureCard = ({ feature, className = "" }: FeatureCardProps) => {
  return <Card className={className}>{feature.caption}</Card>;
};

export { FeatureCard };
```

Right:

```tsx
import type { JSX } from "react";
import { Card } from "@/components/ui/Card";
import type { FeatureCardProps } from "./types";

const FeatureCard = (props: FeatureCardProps): JSX.Element => {
  const { feature, className = "" } = props;

  return <Card className={className}>{feature.caption}</Card>;
};

export { FeatureCard };
```

The same applies to hooks and plain functions that accept an options object:
take the object as one named parameter and destructure it in the body.

## 8. Full typing

Everything is typed explicitly. Do not rely on inference for anything a reader
would have to work out.

- Every function, method, component, hook and callback has typed parameters
  and an explicit return type, including `void`, `Promise<...>` and
  `JSX.Element` (`JSX.Element | null` when it can render nothing).
- Every component has a named props type, even when it has a single prop.
- State, refs, memoized values and context are typed through generics:
  `useState<number>(0)`, `useRef<HTMLDivElement | null>(null)`.
- Module-level constants and data arrays have an explicit type annotation:
  `const testimonials: Testimonial[] = [...]`.
- Event handlers type their event: `(event: React.ChangeEvent<HTMLInputElement>): void`.
- API route handlers type the request, the response body and the return type.
- `any` is forbidden. Use a precise type, or `unknown` narrowed with a check.
- No non-null assertions (`value!`) and no `as` casts to silence the compiler.
  Narrow with a condition or a type guard instead. `as const` is fine.
- Types derived from a zod schema use `z.infer` and are exported as named
  types.

## 9. Where types live

Types are never declared in component, hook, data, route or utility files.

- Every `type` and `interface` lives in a file named `types.ts` inside the
  folder of the thing it describes. Every component folder and every module
  folder has its own `types.ts`; one `types.ts` never collects the types of
  several components:
  - `src/components/ui/Button/types.ts` for `Button`
  - `src/components/sections/Hero/HeroSlider/types.ts` for `HeroSlider`
  - `src/lib/server/rate-limit/types.ts` for the rate limiter
  - `src/app/api/preorders/types.ts` for that route
- Name types after what they describe: `HeroSliderProps`, `SpecRow`,
  `PreorderResponse`. Props types are `<ComponentName>Props`.
- Import types with `import type { ... } from "./types"` inside the same
  folder.
- Types that are part of a component's or module's public interface (props,
  item types such as `TabItem`, variants such as `ButtonVariant`, results such
  as `RateLimitResult`) stay in its `types.ts`. Code that uses the component
  imports them from there:
  `import type { TabItem } from "@/components/ui/Tabs/types"`.
- A type shared by the sub-components of one section lives in the section's
  own `types.ts` (`sections/Preorder/types.ts` for `PreorderReceipt`).
- A domain type used by more than one folder (models, pre-orders, spec rows)
  is a shared type. Shared types live in `src/types/`, one file per domain
  (`src/types/models.ts`, `src/types/preorder.ts`), and are imported through
  the alias: `import type { DroneModel } from "@/types/models"`.
- Before declaring a type, check `src/types/` and the local `types.ts` for one
  that already describes the same thing. Reuse and extend existing types
  instead of redeclaring the same shape.
- `types.ts` files contain only types. Runtime values (constants, zod schemas,
  functions) stay in their own files; the type inferred from a schema is
  exported from the matching `types.ts`.

## 10. Exports

Every file has exactly one export statement, and it is the last statement in
the file. Nothing is ever exported at the top or in the middle of a file. This
applies to every file that exports anything: components, hooks, utilities,
data, `types.ts`, route handlers, pages, layouts and config files.

- Never put `export` in front of a declaration. `export const`,
  `export function`, `export type`, `export interface`, `export enum` and
  `export default function` are all forbidden, at the top, in the middle or at
  the bottom of a file.
- Declare everything without `export`, then list every exported name once at
  the end: `export { firstName, secondName };`.
- `types.ts` files end with `export type { FirstType, SecondType };`.
- Names are listed in the order they are declared in the file. A list that
  does not fit on one line puts each name on its own line.
- A file whose only export is a default export ends with
  `export default Name;`. The value is declared as a named constant first;
  never export an anonymous expression (`export default defineConfig({...})`).
- A file that has a default export and named exports still has one statement:
  the default goes into the list as `Name as default`. `metadata`, `GET` and
  `POST` work from the list.
- Route segment config (`dynamic`, `revalidate`, `runtime`, `maxDuration`,
  `dynamicParams`, `fetchCache`, `preferredRegion`) is the only thing that
  keeps `export const`: Next.js parses these statically and fails the build
  with "It mustn't be reexported" when they come from a list. Such a line is
  still never at the top or in the middle: it sits at the end of the file,
  directly above the final export statement.
- No re-exports in the middle of a file either: `export { ... } from` and
  `export * from` follow the same rule, and barrel files are not used. A
  component's `index.tsx` exports the component it declares and nothing else.

Wrong:

```ts
export const QUANTITY_MAX: number = 5;

const usdFormatter: Intl.NumberFormat = new Intl.NumberFormat("en-US");

export const formatPrice = (priceUsd: number): string => {
  return usdFormatter.format(priceUsd);
};
```

Right:

```ts
const QUANTITY_MAX: number = 5;

const usdFormatter: Intl.NumberFormat = new Intl.NumberFormat("en-US");

const formatPrice = (priceUsd: number): string => {
  return usdFormatter.format(priceUsd);
};

export { QUANTITY_MAX, formatPrice };
```

Wrong:

```tsx
export const metadata: Metadata = {
  title: "MDR - Premium drones",
};

const RootLayout = (props: LayoutProps<"/">): JSX.Element => {
  const { children } = props;

  return <html lang="en">{children}</html>;
};

export default RootLayout;
```

Right:

```tsx
const metadata: Metadata = {
  title: "MDR - Premium drones",
};

const RootLayout = (props: LayoutProps<"/">): JSX.Element => {
  const { children } = props;

  return <html lang="en">{children}</html>;
};

export { metadata, RootLayout as default };
```

Right (route handler with segment config):

```ts
const GET = async (): Promise<Response> => {
  const modelsResponse: ModelsResponse = await getModels();

  return Response.json(modelsResponse);
};

export const dynamic = "force-static" as const;

export { GET };
```

Right (`types.ts`):

```ts
type FeatureIcon = "flight-time" | "range" | "camera" | "weight";

type Feature = {
  icon: FeatureIcon;
  caption: string;
};

export type { FeatureIcon, Feature };
```

## 11. Checklist before finishing

Go through every file you touched:

- No function, method, component, hook or mixin has a one- or two-character
  name; no abbreviations anywhere.
- New folders and files have full, descriptive names.
- Every component is `<ComponentName>/index.tsx` in a PascalCase folder with
  no second `.tsx` file; its `types.ts`, `styles.module.scss` and helpers are
  in the same folder, and nothing that belongs to one component lies outside
  its folder.
- There is not a single comment outside `.env.example`.
- Agent files are in English.
- No nested ternaries, tricks, arbitrary Tailwind variants or deep SCSS
  nesting.
- Every function is an arrow function in a `const`, unless it needs `this`, is
  a generator, has overloads, is generic in a `.tsx` file, or must be hoisted.
- Every component signature is `(props: SomethingProps)` with destructuring in
  the body.
- Every parameter, return value, state, ref and exported constant is typed;
  no `any`, no `!`, no silencing casts.
- No `type` or `interface` outside a `types.ts` file; each component and
  module has its own `types.ts`; shared domain types are in `src/types/`.
- Every file has one export statement and it is the last statement; no
  `export` in front of any declaration, except route segment config placed
  directly above that statement.
- `npm run lint`, `npx tsc --noEmit` and `npm run build` pass.
